# SolidWorks-MCP — форк RBR

Форк [hjbaard/SolidWorks-MCP](https://github.com/hjbaard/SolidWorks-MCP) с расширением RBR.
Все доработки — в подпакете `src/solidworks_mcp/rbr/`; файлы оригинала не изменены.

## Ветки

| Ветка | Содержимое |
|---|---|
| `main` | зеркало `upstream/main`, обновляется автоматически, руками не трогать |
| `rbr` | `main` + расширение RBR; ветка по умолчанию, отсюда ставится сервер |
| `sync/upstream-<sha>` | автоматический мерж новой версии upstream → PR в `rbr` |

## Слежение за upstream

`.github/workflows/upstream-sync.yml` — по понедельникам 06:17 UTC и вручную (Actions → Upstream sync → Run):

1. зеркалит `upstream/main` в `main`;
2. если upstream ушёл вперёд — мержит его в `sync/upstream-<sha>`, гоняет unit-тесты на Windows, открывает PR в `rbr` со списком коммитов и новыми строками CHANGELOG;
3. при конфликте — открывает issue.

`tests/rbr/test_upstream_contract.py` хранит хэши методов оригинала, которые расширение патчит или использует. Если upstream их изменит — тест в PR падает: прочитать изменение, при необходимости поправить `rbr/fastpath.py` / `rbr/journal.py`, обновить хэши `python tests/rbr/test_upstream_contract.py --update`.

Перед мержем PR — живая проверка на SolidWorks: `python -m solidworks_mcp.rbr --selftest`.

**Flow Simulation** (1.5.0). Нужны надстройка Flow Simulation и её API SDK (`<папка Flow>\API\flow simulation api sdk x64.exe`; он регистрирует `NIKCommonApi2`, перезагрузка не нужна). Документ должен быть сохранён: проект Flow лежит рядом с файлом.

| Инструмент | Что делает |
|---|---|
| `flow_create_project(name, template="internal_water")` | проект из шаблона `.fwp` (имя в папке шаблонов Flow или полный путь); расчётная область подгоняется под модель автоматически. Тип задачи и жидкость задаёт шаблон: с Flow идёт только `internal_water`, шаблон для внешнего обтекания воздухом делается один раз в мастере Flow (затем «Создать шаблон») |
| `flow_add_boundary_condition(kind, faces, value=None, name=None)` | входы `inlet_velocity` (м/с), `inlet_mass_flow` (кг/с), `inlet_volume_flow` (м³/с), `inlet_mach`, `inlet_mass_flux`; выходы `outlet_*`; давления `static_pressure`, `total_pressure`, `environment_pressure` (Па); стенки `real_wall`, `real_external_wall`, `ideal_wall` (без значения). Внутренней задаче нужно хотя бы одно условие давления |
| `flow_add_goal(kind, faces, value="average", name=None)` | поверхностная цель: давления, температура, плотность, скорость, расходы, силы и моменты по осям. `value` — `average`/`min`/`max`/`bulk_average`; у интегральных целей (силы, расходы, моменты) его нет |
| `flow_set_conditions(velocity_mps, pressure_pa, temperature_k, mesh_level)` | начальные условия (для внешней задачи — набегающий поток) и уровень автоматической сетки 1…7 |
| `flow_solve(timeout_s=120)` | сохраняет документ, строит сетку, считает, возвращает цели `{name, value, unit}` в СИ и загружает результаты в SolidWorks (узел «Результаты» Flow — там строятся эпюры; сам `Solve` их не загружает). Долгий расчёт отвечает `{job_id, state: running}` → `get_job`. Отказ Flow приходит с его причиной из `%TEMP%\ngp.log` |
| `flow_goals(service=False)`, `flow_info()` | значения целей последнего расчёта; проекты документа, активный проект, его условия и цели |

Грани: `'#5'` (индекс `list_faces`), `'+x'` / `'+x:inner'`, `'all'`, или `['selection']` — то, что выделено в SolidWorks.

Как устроено: все вызовы Flow идут через NIK API в отдельном процессе `rbr/flow_worker.py` — эта библиотека загружается в вызывающий процесс и роняет его access violation (чтение любого параметра расчётной области), так что падает воркер, а не сервер. На время вызова включается тихий режим Flow (`SetSilent` классического API): иначе вопросы «сбросить расчётную область?» / «скорректировать сетку?» ждут клика в SolidWorks. Классический API `FloWorks.App` для построения проекта не годится: выходы, давления и тип цели им не задаются, а `Solve` молча отказывает. Проверено на Flow Simulation 2025 SP3: полая коробка 100×50×20 (стенка 3 мм, вода), вход 1 м/с, выход — давление окружающей среды: расчёт 7 с, расход на выходе −6,16·10⁻⁴ м³/с = 1 м/с × 44×14 мм².

**Полость по обводу** (1.7.0, `rbr/cavity.py`): сечение обвода плоскостью → замкнутый контур → смещение внутрь на стенку → вырез по сечениям или вырез на расстоянии от поверхности.

| Инструмент | Что делает |
|---|---|
| `sketch_intersection(sketch\|plane, faces\|body, detach=True)` | кривые пересечения граней/тела с плоскостью эскиза. 2D `ISketchManager.IntersectCurves` не создаёт ничего (проверено: грани, тело, плоскость + грани, раннее и позднее связывание, с графикой и деревом). Работает `IModelDoc2.Sketch3DIntersections` во вспомогательном 3D-эскизе (выделены плоскость и грани) + `SketchUseEdge3` в 2D-эскиз — та же длина. `detach=True` удаляет связь «На кромке» (иначе кривые не режутся) и сам 3D-эскиз |
| `sketch_trim_region(sketch, keep_box)` | `keep_box` в мм модели: `{'x': [-114, 114]}` (любые из x/y/z, `None` — открытая сторона) или два угла. Стороны рамки — прямые в эскизе; кривая оставляет часть внутри рамки, прямая — часть внутри кривой; обрезка — power trim (`SketchTrim` closest) по середине самого длинного внешнего участка, пока такие есть. Итог проверяется: одна область |
| `sketch_offset_chain(sketch, distance_mm, inward=True)` | `SketchOffset2` всей замкнутой цепи, сторона проверяется по контуру (не та — удаляется и повторяется со знаком наоборот), исходник → вспомогательная геометрия, один размер смещения (`link_to` — глобальная переменная). `wall_mm` — измеренные min/max |
| `split_line_project(sketch, faces)` | линия разъёма проецированием. `InsertSplitLineProject` создаёт элемент, только если эскиз выделен с меткой 4, грани — с меткой 1, и отвечает `None` и при успехе — доказательство: новая фича и число граней |
| `loft_cut(sketches, guides=None)` | вырез по сечениям (`InsertCutBlend`, профили метка 1, направляющие метка 2); не убравший материал — откат |
| `cut_offset_from_surface(sketch, face, offset_mm, toward)` | вырез до «на расстоянии от поверхности» (end condition 5, грань меткой 1), в т.ч. до участка, ограниченного линией разъёма; `offset_reverse`, `translate` |

Скорость: внутри открытого эскиза каждый COM-вызов без `CommandInProgress` в ~20 раз дороже (64 точки на 5 сегментах — 15 с против 0,7 с). Флаг снимается только на открытие/закрытие эскиза (`InsertSketch`/`EditSketch`), выборка кривых — одним `GetTessPts` на половину кривой, перевод точек в модель — в Python по осям эскиза. Обрезка 6 кусков: 115 с → 5 с.

Ограничение «на расстоянии от поверхности» (и «до поверхности»): нужна ОДНА грань, которая целиком закрывает профиль по направлению выреза. На реальном крыле (227 граней) профиль сечения смотрел сразу на верхнюю и нижнюю обшивку — SolidWorks отказывал и без линии разъёма, и с ней; работал только `translate=True` (плоский торец). Отказ `cut_offset_from_surface` теперь сам пускает лучи из контура и называет грани впереди (`faces_ahead`) с советом: профиль на одну грань, `translate` или `loft_cut` по сечениям.

Откат (`rbr/fastpath.py`, 1.7.0): неудавшийся вызов удалял новые фичи вместе с поглощёнными (`SW_DELETE_ABSORBED`) — и эскиз, существовавший ДО вызова, если новая фича его поглотила (линия разъёма из эскиза человека + отказавший в том же вызове вырез — эскиз пропал). Фича, поглотившая старую, теперь удаляется одна, эскиз возвращается в дерево; новые поглощённые удаляются вторым проходом.

На большой детали: перед `Sketch3DIntersections` выделяются только грани, чья габаритная рамка пересекает плоскость (плоскость читается из `IRefPlane.Transform`, без открытия эскиза): крыло, 227 граней → 4, пересечение 48 → 18,6 с.

Проверено на SW 2025 SP3 (лофт по Z из трёх окружностей Ø200/300/180, плоскости Z 150 и 250, рамка X ±114, стенка 6 мм): контур X ±108, стенка 5,96…6,03 мм по точкам, площадь 53 743 мм² (оценка A − P·d + углы); вырез по двум сечениям убрал 5 321 364 мм³ при оценке по средней площади 5 319 400; карман до плоского участка линии разъёма — ровно π·30²·144 мм³; до криволинейного участка обвода — 6,000 мм по нормали от дна кармана до участка. На реальном крыле (74 фичи, плоскости Z −300 и −200, рамка X ±114, стенка 6 мм): контур 6 сегментов (4 сплайна + 2 прямые) X ±114 → после смещения X ±108, Y точно на 6 мм внутри, стенка 5,91…6,07 мм по точкам, площадь 17 739 → 14 494 мм²; вырез по сечениям Z −300…−200 убрал 1 259 326 мм³ (оценка по средней площади 1 267 300); стенка посередине (Z −250) 6,4…7,1 мм — линейный переход между сечениями под выпуклой обшивкой, чаще сечения — ближе к 6.

|---|---|
| `body_properties(bodies=None)` | по каждому телу: объём, площадь, масса и центр масс (`IMassProperty.AddBodies`; объём и площадь он при этом отдаёт нулём — они из `IBody2.GetMassProperties`), габарит, грани, видимость, материал |
| `rename_body(body, new_name)` | `IBody2.Name` записывается и переживает перестроение |
| `show_bodies(bodies, visible)` | `IBody2.HideBody`, проверка через `Visible` |
| `delete_bodies(bodies, keep=False)` | фича «Удалить/сохранить тело» (`InsertDeleteBody2`) |
| `move_copy_body(bodies, translate_mm, rotate, copies)` | фича «Переместить/копировать тело» (`InsertMoveCopyBody2`). Замерено: углы `RotAngleX/Y/Z` поворачивают вокруг Z, Y, X (в таком порядке), а при повороте перенос в той же фиче игнорируется — поворот и перенос делаются двумя фичами. Перемещённое тело SolidWorks называет по фиче; имя возвращается, тела сопоставляются по ожидаемому центру масс |
| `set_feature_scope(feature, bodies)` | область действия выреза/бобышки/вращения/отверстия: `AccessSelections` → `FeatureScope`, `AutoSelect=False`, `FeatureScopeBodies` → `ModifyDefinition`; объёмы тел до/после |
| `save_bodies(bodies, path)` | `IPartDoc.SaveToFile3` с выделенными телами (новая деталь, связанная с исходной, которая должна быть сохранена). `CreateSaveBodyFeature` отвечал `None` во всех вариантах |
| `insert_part(path, config, name)` | `IPartDoc.InsertPart3` (только тела); два вставки одного файла дают тела с одинаковым именем — новые переименовываются `name`, `name_2`… |

Материал на тело через API не назначается: `IBody2.SetMaterialProperty` отвечает «нет ошибки» (1), но ни имя, ни масса не меняются (SW 2025 SP3, также из отдельного COM-клиента; известная проблема форума SolidWorks). Тела несут материал детали, `body_properties` показывает, откуда он.

**SolidCAM** (1.8.0, `rbr/solidcam.py`) — через API автоматизации SolidCAM 2.0 (`scautom2.dll`): `Launcher.Item(0)` — `IApplication` того SolidCAM, что работает (`solidcam.exe`) под SolidWorks пользователя. Второй SolidWorks / SolidCAM не запускается никогда. Старый API (`scautom.dll`, `ISolidCAM`/`IAutomation`) при создании в процессе сервера уронил его — не используется.

| Инструмент | Что делает |
|---|---|
| `solidcam_status()` | версия, станки, шаблоны операций, открытая CAM-деталь |
| `solidcam_zero(up='+z')` | система координат SolidWorks `SolidCAM_Zero`: на верхней грани в левом нижнем углу габарита (min X, min Y, max Z); точка — в 3D-эскизе с `AddToDB` (без него точка прилипает к началу) |
| `solidcam_new_part(path, machine)` | ноль → `CreateNewMillingPart`. SolidCAM открывает панель «Milling Part Data» и ждёт человека: переданную систему координат нулём он НЕ делает. В панели: «Ноль детали» → «Выберите систему координат» → `SolidCAM_Zero` → ✓ ✓ ✓ |
| `solidcam_open(path)` | открыть `.prz` |
| `solidcam_add_zero(position \| coordinate_system)` | `Homes.Create(TopCorner/TopCenter/CADOrigin)` / `CreateFromCAD` |
| `solidcam_stock(offsets_mm)` | заготовка-параллелепипед (`CreateStockBox(Default)`) |
| `solidcam_add_operation(template, geometry, home)` | операция из шаблона (`ITemplate.CreateOperation`) |
| `solidcam_calculate(operations, force)` | расчёт траекторий |
| `solidcam_gcode(operation, path)` | G-код (вся деталь → `<папка .prz>\G-codes`, или одна операция) и проверка файла: строки, рабочие ходы (G1/G2/G3, циклы G81–G89), позиции-заглушки `142857` |
| `solidcam_save`, `solidcam_close` | сохранить / закрыть CAM-деталь |

Ограничение API: геометрию операции (цепочку, набор граней) он не создаёт. Операция из шаблона на одной лишь цели (3D-модели) рассчитывается и постпроцессируется, но программа без ходов — `solidcam_gcode` предупреждает. Геометрию задают в SolidCAM, инструменты затем ссылаются на неё по имени. Проверено на SolidCAM 2025 SP2 HF1 в SOLIDWORKS 2025 SP3: деталь 100×60×20 с карманом, станок `gMilling_3x`, ноль `SolidCAM_Zero` (0, 0, 20), заготовка по умолчанию, торцевание D50 + 3D-контур D10 + сверление D6 из шаблонов → расчёт → `.NC` 41 строка.

**Система координат эскизов** стандартных плоскостей RU-шаблона («Спереди», «Сверху», «Справа»):
- Спереди: (sx, sy) = (X, Y);
- Справа: (sx, sy) = (−Z, Y);
- Сверху: (sx, sy) = (X, −Z).

`InsertRefPlane`: флаг разворота плоскости — `8 + 256` (reverse + distance); `ReverseDirection` через `ModifyDefinition` плоскость НЕ переворачивает — пересоздавайте с флагом.

## Установка (Windows)

```powershell
git clone -b rbr https://github.com/RomanBRempel/SolidWorks-MCP.git $HOME\source\SolidWorks-MCP
uv tool install --force --editable $HOME\source\SolidWorks-MCP
```

Конфиг MCP-клиента (`claude_desktop_config.json`):

```json
"solidworks": {
  "command": "C:\\Users\\<user>\\AppData\\Roaming\\uv\\tools\\solidworks-mcp\\Scripts\\python.exe",
  "args": ["-m", "solidworks_mcp.rbr"]
}
```

numpy для скриптов (`np` в `run_script`): `uv tool install --force --editable <путь> --with numpy`.

Обновление: `git -C $HOME\source\SolidWorks-MCP pull` и перезапуск клиента (editable — переустановка не нужна).
